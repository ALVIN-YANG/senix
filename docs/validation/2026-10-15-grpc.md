# gRPC 双向流与摘流验收

日期：2026-10-15。基线提交：`3bffc5c5fe5cd5255abfcc66f4e83272329c4db8`。本轮使用其后的当前源码，补充真实进程协议回归和证据；未修改代理实现、接口或依赖。此前的 `application/grpc` 请求头分类测试仍保留，不能单独证明 gRPC 消息能完整转发。

## 实际链路

`h2` 客户端 → TLS / HTTP2 → 真实 `senixd` → TLS / HTTP2 → 隔离 gRPC Echo 后端。客户端和后端都断言 ALPN 为 `h2`。客户端信任本次生成的测试证书并检查 `example.test` 主机名；上游使用自签名测试证书，按现有测试配置关闭上游证书校验。这不构成公网 CA 校验或 mTLS 的验收。

报文遵循 [gRPC over HTTP2 官方协议](https://grpc.github.io/grpc/core/md_doc__p_r_o_t_o_c_o_l-_h_t_t_p2.html)。请求使用 POST、服务/方法路径、`te: trailers`、`application/grpc+proto` 与自定义元数据。消息是未压缩的五字节长度前缀，加上 `message Echo { string text = 1; }` 的有效 Protobuf 编码。测试手动生成固定消息，使用项目现有 `h2` / OpenSSL 依赖，不依赖生成的 gRPC SDK。

| 检查 | 结果 |
| --- | --- |
| 双向流 | 请求半流尚未结束时，先收到包含中文的第一条响应；摘流后再发送第二条请求消息，收到完整响应后才结束 RPC。 |
| DATA 边界 | 请求和响应都在 gRPC 长度前缀内部拆成两次 DATA 写入；接收端按消息长度重组，不依赖单个 DATA 帧包含完整消息。 |
| 元数据 | 后端核对请求内容类型、TE、路径和自定义头；客户端核对响应内容类型和自定义头。 |
| 成功 trailers | 第一项测试收到 `grpc-status=0`、包含百分号编码中文的 `grpc-message`、二进制元数据 `proof-bin=AAEC/w==` 和流结束。 |
| 错误 trailers | 第二项测试仍为 HTTP 200，但结束 trailers 的 `grpc-status=7` 原样到达；其余消息、元数据与结束标志也保留。未把 HTTP 200 当作 RPC 成功。 |
| 摘流 | 两项测试均在第一条响应到达后摘除 A，此时普通在途为 0、长连接为 1。三个新普通请求都由 B 响应，原 RPC 在 A 上完成第二条双向消息；结束后为 `DRAINED`，两类在途归零。 |
| 耗时指标 | 长连接耗时直方图完成次数在流存续期间为 0，RPC 结束后为 1；成功和非零 RPC 状态分别验证。 |

## 边界

这是 gRPC 线上报文格式的功能验收，未使用 grpc-go、grpc-java、grpc-js 等生成式客户端，不作为各 SDK 的互操作认证。每项测试只有一条双向 RPC、两条请求/响应消息和三个摘流后的普通请求。没有覆盖压缩、Trailers-Only 提前错误、取消/截止时间、慢消费者、流控压力、连接复用或大消息。

本轮没有测量流式吞吐、首条消息延迟、最大并发或长期稳定性，也未重测已发布安装包与镜像。当前指标只按 HTTP 结果和代理错误统计；保留非零 `grpc-status` 不等于已有 RPC 状态指标。已有性能图仍以各自原始提交和环境为准，不能据此推导 gRPC 容量。
