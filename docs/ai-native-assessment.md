# AI 使用能力核查

日期：2026-10-15。Senix 的 AI 方向是让 Agent 使用受限工具管理网关，不能把存在 MCP 端点等同于任意模型都能可靠完成运维，也不把通用反向代理宣传成 LLM API 路由产品。

## 已有与本轮证据

| Agent 所需能力 | 当前状态 | 证据 |
| --- | --- | --- |
| 发现可用动作 | `tools/list` 按动作/资源范围裁剪，调用时再授权 | 真实 MCP E2E |
| 读取真实状态 | 实例、诊断、配置版本与完整配置、变更、证书元数据、审计 | 当前配置读取为本轮新增；完整配置需要全局 `change.read` |
| 在执行前检查影响 | 校验完整候选配置、结构化差异、摘要、不可修改计划 | Owner 只批准精确内容，15 分钟有效 |
| 人工批准后执行 | AI 只有应用已批准计划的工具；过期基线拒绝，重复应用返回原版本 | [实际流程记录](validation/2026-10-15-ai-configuration.md) |
| 处理失败 | 稳定错误码、证据、可读取操作状态 | 指南覆盖权限、批准、过期与并发重读 |
| 小上下文接入 | [llms.txt](../llms.txt) 和单一工作流指南 | 文档索引；不宣称所有客户端自动读取它 |
| 可观测与性能核查 | 标准指标、可选 JSON 日志、原始基准数据 | [监控指南](observability.md)、[基准脚本](../benchmarks/README.md) |

## 还应补的内容，按优先级排序

1. **让完整配置候选有类型，并把读取版本带入规划请求。** 当前 `candidate` 是任意 JSON，字段错误需到规划时才发现。读取 v1 后如被别人发布 v2，再提交基于 v1 构建的完整候选，规划会以当时最新版本为基线；调用方必须比较 `base_version` 与读取版本并重读合并。应在下一份接口变更中加入明确的 `expected_version` 和配置 JSON Schema，再验证并发发布不会覆盖无关修改。现有批准/STALE_PLAN 保护不覆盖这个读取到规划的窗口。
2. **建立 Agent 任务评测，而不仅是工具测试。** 固定任务集应覆盖“只改一个域名、保留无关路由”“不健康实例回接”“批准过期”“权限不足”“并发变更后重新合并”。目前验证了当前 AI 助手的真实 MCP 调用、Owner 批准与请求结果，还没有多个客户端/模型的成功率、错误恢复率和误操作率数据。
3. **补齐需要跨服务定位问题时的追踪。** 当前已有指标和日志路径，没有原生 trace/span 或 OTLP trace 输出；接入 OTel metrics receiver 不等于完整 APM。应先确定上下文传播、采样、敏感字段和长流 span 生命周期，再实现 Tempo/Jaeger 等后端验证。
4. **扩展性能证据的代表性。** 当前固定 1 KiB、HTTP/HTTPS、1/100 路由、短时闭环并发。长期稳定性、大响应/请求体、SSE/WebSocket/gRPC、故障切换和流量中发布配置仍需要独立负载模型；也应在 Linux 独立服务器上重测。不能将本机基准解释为容量保证。

以上是后续候选范围，尚未实现。对外推荐先展示“可读状态 → 可审查计划 → 人工批准 → 结果证据”的完整路径，再收集用户首次运行成功率、重复使用和问题反馈；Star 数是后续结果，不是当前技术验证的通过条件。
